# Task 0035: Pre-1.0 release qualification

## Status

In progress — Slices A–E are complete; Slice F screenshots and release-candidate
qualification remain

## Context

Wevva 0.4.4 is the latest tagged release, but the application has changed
substantially since then. The Dashboard is now the navigation hub; the Weather
screen has a tested responsive layout; the Alerts Centre, saved-locations world
map, global tropical workspace, persistent warning cache, background refresh,
and contextual help are implemented. The public Python imports remain
recognizable, configuration migration has regression coverage, and the package
can build both an sdist and a wheel containing its runtime geographic data.

The completed feature work is substantial enough to justify a 1.0 lifecycle.
That version should mean that the documented CLI, public Python imports,
persisted preferences, and principal TUI paths form a dependable release—not
that every proposed map or warning feature is complete.

A release review on 6 November 2026 found a small number of concrete gates.
The first of those gates was completed on 7 November 2026: sibling Task 0018
now records an explicit outcome for every provider slice, and clean commit
`591c69ec962acc022522ff33d8169f85ddde3cce` is tagged and released as
`wevva-warnings` 0.6.0. The remaining release state is:

- `wevva-warnings==0.6.0` is now the declared and locked registry dependency.
  On 8 November 2026, PyPI served its version metadata and wheel, a locked sync
  replaced the editable sibling install, and Wevva's required tropical imports
  loaded from the installed release;
- the four deterministic tropical-context failures recorded in Task 0031 are
  resolved; the focused geometry, sidebar, layout, Tropical Systems, and
  Dashboard suites now pass, while the complete candidate suite remains a
  Slice G check;
- the released JMA, CMA, HKO, Météo-France Réunion, NHC/CPHC, and prose-product
  shapes are now qualified through one shared structured reader with separate
  Analysis, Forecast, and Extents views where the supplied data warrants them;
- Task 0021's bounded pre-1.0 policy now prevents foreign focused-map context,
  category monopolization, repeated names, and forced overlapping political
  labels; its larger gazetteer and explicit hierarchy work remains deferred;
- release-facing README copy and screenshots do not consistently represent the
  Dashboard-era application.

This task coordinates those existing boundaries into one finite release gate.
It does not reopen every proposed task or turn 1.0 into a feature-completeness
claim.

## Problem

The former dependency mismatch is resolved: the upstream stabilization work is
complete in `wevva-warnings` 0.6.0, and Wevva now locks its published wheel
without access to the sibling checkout. The application must still qualify its
structured tropical reader against that released contract rather than against
an editable or provider-specific intermediate shape.

The documented Wevva regression command is also red, and two prominent new
surfaces still have known presentation defects: tropical maps can lose useful
surrounding context, while structured provider facts are hard to scan in their
current generic tab content. The Alerts Centre can likewise show misleading or
illegible contextual labels in demonstrated fixtures.

At the same time, completing every open task would unnecessarily delay a useful
release. Pan and zoom, an all-storm overview, saved-location warning badges,
denser gazetteers, and a more ambitious cartographic grammar are additions to a
working product rather than prerequisites for 1.0.

## Desired outcome

With the sibling library's bounded tropical-centre information review complete,
released as 0.6.0, and consumed from the package index, qualify the shared
Wevva presentation against the complete released data matrix rather than the
JMA shape alone.

The resulting clean 1.0 release candidate installs without sibling checkouts,
passes both projects' deterministic checks, presents tropical data and maps at
the quality expected of a headline workspace, avoids the demonstrated
focused-alert label failures, and accurately documents the application being
released.

The release candidate should be tested from built artifacts and through a short
manual terminal journey. Actual publication remains an explicit maintainer
action.

## Dependency and sequencing

The order is a hard task dependency, not merely a suggested implementation
sequence:

1. Complete sibling `wevva-warnings` Task 0018 and the already implemented NHC
   work referenced by Wevva Task 0022. **Complete in `v0.6.0`.**
2. Freeze, version, test, and publish the resulting warning-library contract.
   **Complete: PyPI serves 0.6.0.**
3. Remove Wevva's editable override and consume that released dependency once
   0.6.0 resolves normally from the package index. **Complete on 8 November
   2026.**
4. Format the released structured tropical data in Wevva, using the final
   cross-provider fixture matrix. **Complete on 8 November 2026.**
5. Complete the remaining Wevva release gates and qualify the 1.0 artifacts.

"Complete" does not require forcing an implementation for every investigated
endpoint. The sibling task already permits evidence-backed no-go decisions for
credentialed, unstable, image/PDF-only, insufficiently attributable, or
geometry-inventing candidates. It does require a recorded outcome for every
slice in that task, stable public data shapes for every implemented enrichment,
updated capability/source documentation, and a clean green sibling build. A
temporarily quiet live endpoint may constrain verification, but it must not be
silently treated as either supported or permanently rejected.

## Approach

1. Complete the sibling structured tropical-provider task before designing the
   final Wevva presentation. Every candidate must have an implementation,
   no-go, or explicitly evidence-limited outcome; "not yet reviewed" is not a
   release outcome.
2. Freeze the resulting public behavior and commit boundary. The dependency may
   remain editable while its own task is active, but Wevva presentation work
   starts only after the sibling schema, fixtures, documentation, suite, and
   build are stable.
3. Publish and consume that warning-library release, then remove the editable
   source. Qualify Wevva against the dependency ordinary users will install.
4. Inventory the complete released structured-data matrix and design the shared
   reader from its common semantics. Use JMA to prove the richest layout without
   turning JMA's field shape into a universal provider abstraction.
5. Resolve the shared viewport regression through Task 0031, independently of
   provider presentation but against the same final tropical fixture set.
6. Complete only Task 0021's existing-data policy slice for alert maps. Inspect
   its motivating fixtures before deciding that larger data or cartographic
   work is necessary.
7. Run the focused suites after each slice, then the complete suites before
   changing release metadata.
8. Update version, README, release notes, and candidate artifacts late so they
   describe the verified result rather than an intended one.
9. Stop and report any unavailable live-provider check. Deterministic fixtures,
   clean installation, and a green suite are hard gates; exhaustive live global
   provider coverage is not.

## Decisions and notes

- `1.0.0` marks a dependable application/API lifecycle, not the end of feature
  development. Existing proposed tasks remain legitimate post-1.0 work.
- A red deterministic suite is a release blocker even when the underlying issue
  is primarily visual. The four recorded tropical failures expressed intended
  context behavior and were resolved through Task 0031 and Slice D.
- Sibling Task 0018 is upstream of the dependency release and the Wevva
  presentation work. Its remaining endpoint decisions are part of this release
  gate; JMA is not treated as an isolated final schema.
- The sibling library owns faithful acquisition and preservation of tropical
  facts from every issuing centre. Wevva owns how the released facts are
  grouped, labelled, wrapped, and shared between its two tropical readers.
- An evidence-backed no-go can complete an upstream investigation. An
  unexamined slice, undocumented intermediate schema, or provider workaround in
  Wevva cannot.
- Provider-native terminology and alternate units may be displayed more
  clearly, but presentation must not silently reinterpret them.
- Task 0021 Slice A is the alert-map release gate. Its data-source and
  cartographic expansions are not.
- No new task is required for each release checklist item; this task is the
  coordination and qualification record.
- Publishing `wevva-warnings` or Wevva remains a separate explicit approval at
  the moment the external action is taken.
